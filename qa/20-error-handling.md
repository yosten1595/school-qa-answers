# Q20. エラーハンドリング

## 問題

API呼び出しが失敗した場合（ネットワーク障害やサーバーエラーなど）、

アプリはどのように対処すべきですか？

## 回答

API 呼び出しの失敗には、通信そのものの失敗(ネットワーク障害、タイムアウト)、400 番台(入力の不正など、リクエストを出した側の問題)、500 番台(サーバー内部のエラーなど、サーバー側の問題)があり、種類によって対処が変わります。アプリは、次のように対処すべきです。

- 失敗を検知する: 通信の失敗や、ステータスコードを見て、失敗したと判断します。失敗を無視して成功したように扱うと、画面とデータがずれます。
- 利用者に分かる形で知らせる: 何が起きたか、次に何をすればよいかを伝えます。サーバーの内部情報や技術的なエラー文は、そのまま見せません。
- 入力内容を消さない: 保存に失敗しても、利用者が入力した内容は残し、打ち直しをさせません。
- 再試行の道を用意する: 通信の失敗や 500 番台は、一時的なことが多いため、再試行できるようにします。400 番台は、入力を直さない限り同じ失敗になるため、再試行ではなく入力の修正を促します。
- 待ち続けない: 返事が来ないときは、時間切れ(タイムアウト)を設けて失敗として扱い、「読み込み中」のままにしません。

このアプリで「新しいタスクを作成」に失敗した場合は、次のようになります。ネットワークが切れていれば、通信できなかったことを知らせ、入力したタスク名は残して再試行できるようにします。400 で返ってきたときは、タスク名の入力を促します。500 で返ってきたときは、サーバーで問題が起きたことを知らせ、しばらくしてからの再試行を案内します。

API 呼び出しが失敗したときは、失敗の種類を見分けて、利用者に分かる形で知らせ、入力を残したうえで、再試行か修正のどちらが必要かを案内すべきだと理解しました。

## 理解のメモ

- 失敗の種類は、通信そのものの失敗、400 番台(リクエスト側の問題)、500 番台(サーバー側の問題)。
- 対処は、検知する、分かる形で知らせる、入力を消さない、再試行の道を用意する、タイムアウトを設ける。
- 再試行は、通信の失敗と 500 番台に向く。400 番台は入力の修正を促す。
- サーバーの内部情報や技術的なエラー文は、利用者にそのまま見せない。
