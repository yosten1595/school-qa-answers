# Q31. コミットメッセージの重要性

## 問題

例：

`feat: ログイン機能を追加`

良いコミットメッセージを書くことがなぜ重要ですか？

## 回答

コミットメッセージは、コミット(変更の記録)に付ける短い説明文で、履歴には変更の中身と一緒にこのメッセージが並びます。例の `feat: ログイン機能を追加` は、`feat:` が変更の種類(新機能)を、そのあとが何をしたかを表していて、種類と内容が一目で分かる整った書き方です。

良いコミットメッセージを書くことが重要なのは、次の理由からです。

- 履歴を読んで何が起きたか分かるため: メッセージだけで変更の概要が分かり、毎回コードの差分を開かなくて済みます。
- 不具合の原因を探しやすいため: いつ、どの変更で壊れたかを履歴から探すとき、メッセージが手がかりになります。
- 戻す変更を選びやすいため: 取り消したい変更を、メッセージで見つけられます。
- レビューしやすいため: レビューする人が、変更の意図を先に把握できます。
- チームで共有しやすいため: 他の人が、自分のいない間の変更を履歴から追えます。数か月後の自分も、他の人と同じ立場になります。
- 記録として使えるため: 変更の種類をそろえておくと、変更点の一覧を自動で作れます。

たとえば、「修正」や「いろいろ変更」では、履歴を見ても何が変わったのか分かりません。「fix: タスク名が空のとき保存できない不具合を修正」のように、種類と内容が分かるメッセージなら、履歴を見るだけで変更の目的が分かります。

このリポジトリでは、`Add answer for Q2 IP address and port (#1)` のように、英語の命令形で何をしたかを書き、末尾の `(#1)` でどの Issue に関連する変更かを示しています。`feat:` のような目印は付けていませんが、何をしたかが分かるという目的は同じです。書き方は、チームやプロジェクトのルールで決まります。

良いコミットメッセージは、履歴から何が起きたかを読み取れるようにするためのもので、原因探し、取り消し、レビュー、共有を楽にするので重要だと理解しました。

## 理解のメモ

- コミットメッセージ = コミットに付ける短い説明文。履歴に変更の中身と一緒に並ぶ。
- `feat:` は変更の種類(新機能)を表す目印。ほかに `fix:`(不具合の修正)、`docs:`(ドキュメントの変更)、`refactor:`(動きを変えない整理)などがある。
- 重要な理由は、履歴を読んで何が起きたか分かる、原因を探しやすい、戻す変更を選びやすい、レビューしやすい、チームで共有しやすい、記録として使える。
- 悪い例は「修正」「いろいろ変更」。良い例は種類と内容が分かるもの。
- このリポジトリでは、英語の命令形で何をしたかを書き、末尾の `(#1)` で関連する Issue を示している。書き方はチームやプロジェクトのルールで決まる。
