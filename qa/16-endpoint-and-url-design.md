# Q16. エンドポイントとURL設計

## 問題

このアプリには以下のAPIがあります。

- `/api/tasks`
- `/api/tasks/{id}`

このようなURL設計の考え方を説明してください。

`{id}` の部分は何ですか？

## 回答

`/api/tasks` や `/api/tasks/{id}` は、バックエンドの API の窓口の宛先で、エンドポイントといいます。フロントエンドがリクエストを送るときに、この宛先を指定し、バックエンドは届いた宛先を見て、対応する処理を実行します。

URL 設計の考え方は、URL で「何を扱うか」を表し、「どうするか」は HTTP メソッドで表すことです。URL には、取得や作成といった動詞を入れず、扱うもの(リソース)の名前を入れます。ここでは `tasks`(タスク)で、複数形で書くのが一般的です。また、階層で範囲を絞り込みます。`/api/tasks` は「タスク全体」、`/api/tasks/{id}` は「そのうちの特定の1件」です。

同じ URL でも、メソッドが違えば別の操作になります。一般的には、次のような組み合わせで使います。

- `/api/tasks` に GET: タスクの一覧を取得する。
- `/api/tasks` に POST: 新しいタスクを作成する。まだ id がないので、全体の URL を使う。
- `/api/tasks/{id}` に GET: 特定の1件を取得する。
- `/api/tasks/{id}` に PUT / PATCH: 特定の1件を、丸ごと置き換える / 一部だけ修正する。
- `/api/tasks/{id}` に DELETE: 特定の1件を削除する。

`{id}` は、タスク1件ごとに付けられた固有の番号(識別子)が入る場所です。波括弧は、ここに実際の値が入ることを示す目印です。たとえば `/api/tasks/5` は「5番のタスク」を指します。id は、タスクを作成したときにバックエンドが付けるのが一般的です。id があるので、同じタイトルのタスクが複数あっても、1件を確実に指定できます。

URL で扱う対象を、メソッドで操作の種類を表し、`{id}` で特定の1件を指定することで、少ない窓口で多くの操作を分かりやすく表せると理解しました。

## 理解のメモ

- エンドポイント = バックエンドの API の窓口の宛先(URL のパスの部分)。フロントエンドが宛先を指定し、バックエンドが対応する処理を実行する。
- URL は「何を」、HTTP メソッドは「どうする」。URL には動詞を入れず、リソースの名前(`tasks`、複数形)を入れる。
- `/api/tasks` = タスク全体、`/api/tasks/{id}` = 特定の1件。新規作成は id がないので全体の URL に POST する。
- `{id}` = 1件ごとの固有の番号が入る場所(プレースホルダー)。例: `/api/tasks/5`。
- エンドポイントの先はバックエンドの処理で、データベースにつなぐのはその処理。保存されたデータを必要とする処理だけがつなぐ。
