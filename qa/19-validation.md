# Q19. 入力チェック（バリデーション）の多重防御

## 問題

入力チェックはフロントエンドとバックエンドの両方で行うべきと言われています。

なぜ片方だけでは不十分なのですか？

## 回答

入力チェック(バリデーション)は、利用者が入力した内容が正しい形・範囲かを確かめることです。フロントエンドとバックエンドでは目的が違い、それぞれに弱点があるため、片方だけでは不十分です。

フロントエンドでのチェックの目的は、利用者の使いやすさです。入力ミスをその場で知らせられ、サーバーに送る前に弾けるので、無駄なリクエストも減らせます。しかし、フロントエンドのプログラムは利用者のブラウザに配られるため、利用者が自由に書き換えたり、飛ばしたりできます。また、画面を通さずにバックエンドの API を直接呼ぶこともでき、その場合はフロントエンドのチェックを通りません。そのため、フロントエンドだけでは、悪意のある入力や想定外の入力を止められません。

バックエンドでのチェックの目的は、不正な入力を最終的に必ず止めて、安全とデータの正しさを守ることです。しかし、バックエンドだけだと、入力ミスの結果が分かるのは、リクエストを送って返事が返ってきてからです。毎回サーバーまで往復する必要があるため、利用者には遅く感じられ、無駄なリクエストも増えます。

そこで、両方で行います。片方が破られても、もう片方で止められるようにする考え方を、多重防御といいます。本当の防御はバックエンドが担当し、フロントエンドはその手前の案内役です。

このアプリでは、「新しいタスクを作成」でタスク名が空のままボタンを押すと、フロントエンドが入力を促す表示を出します。もし誰かが画面を通さず、空のタスク名で API を直接呼んでも、バックエンドがチェックして、400 のステータスコードで返します。

フロントエンドは使いやすさのための案内で、バックエンドは最終的に必ず止める防御であり、フロントエンドは飛ばされることがあるので、バックエンドのチェックが必須だと理解しました。

## 理解のメモ

- バリデーション = 入力内容が、正しい形・範囲かを確かめること。
- フロントエンドのチェック = 使いやすさのための案内(すぐ知らせる、無駄な送信を減らす)。弱点は、書き換えたり飛ばしたりできること。
- バックエンドのチェック = 最終的に不正な入力を必ず止める防御(安全、データの正しさ)。弱点は、結果が分かるのに往復の時間がかかること。
- 多重防御 = 片方が破られても、もう片方で止められるようにする考え方。本当の防御はバックエンド。
- このアプリでは、空のタスク名はフロントエンドが促し、API を直接呼ばれてもバックエンドが 400 で返す。
